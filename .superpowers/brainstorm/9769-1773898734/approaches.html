Three architectural approaches

When does the world get built? This drives everything else.

A

All-upfront generation

At session start: build the full world graph (all zones, rooms, connections, gate positions), then fire parallel Claude calls to generate every room description. Player waits ~8–12s before the game begins.

Pros

  • Zero mid-game pauses
  • Descriptions can reference the full world
  • Simplest session logic

Cons

  • Long startup wait
  • Generates rooms player may never visit
  • Costly (all Claude calls upfront)
B

Lazy on first visit

At session start: build the world graph instantly (no Claude calls). Room description generated on first visit — player sees a ~1–2s pause each time they enter a new room for the first time.

Pros

  • Fast startup
  • Only pays for rooms visited
  • Description has player context

Cons

  • Pause on every new room
  • Pause is most noticeable during exploration
  • Harder to handle errors mid-scene
C

Zone-ahead generation ✦ recommended

At session start: generate Act 1 only (3–5 Claude calls, ~3s). When player enters any room in a zone, generate the next zone in the background. By the time they reach the gate, the next zone is ready.

Pros

  • Fast startup (~3s, same feel as now)
  • No mid-game pauses in practice
  • Only generates zones the player reaches
  • Matches existing tile prefetch pattern

Cons

  • More orchestration complexity
  • Gate blocked briefly if player rushes through a zone

What stays the same in all three

  • Room latents come from a hand-authored template library (one set per room type)
  • Slot-filling (LOCATION, CHARACTER, etc.) still handles narrative variability
  • The Act 2 fork, gate mechanic randomization, and grid layout are decided at world-gen time
  • Session code, command processor, latents processor — mostly unchanged
